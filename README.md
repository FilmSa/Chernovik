

# 4. Локальная балансировка нагрузки

## 4.1 Схема балансировки

Внутри дата-центра используется двухуровневая схема балансировки:

**L4-балансировщик (единая точка входа):**

| Параметр           | Описание                                                  |
| ------------------ | --------------------------------------------------------- |
| **Назначение**     | Распределение входящего трафика между L7-балансировщиками |
| **Принцип работы** | Балансировка TCP-соединений по IP:port                    |
| **Реализация**     | Virtual IP (VIP) + L4-балансировка                        |
| **Алгоритм**       | round robin                                               |
| **Резервирование** | Active/Standby (Keepalived)                               |

---

**L7-балансировщик (NGINX):**

| Параметр           | Описание                                                      |
| ------------------ | ------------------------------------------------------------- |
| **Реализация**     | Кластер серверов NGINX |
| **Функции**        | SSL Termination, маршрутизация запросов, балансировка backend |
| **Алгоритм**       | round robin                                                   |
| **Кэширование**    | Кэширование статических и часто запрашиваемых данных (tiles)  |
| **Резервирование** | Схема N + 1                                                   |

---

### Схема обработки запросов

```text
User
  ↓
L4 (VIP)
  ↓
один из 6 NGINX
  ↓
по URL:
  /api    → api
  /search → search
  /route  → route
  /tiles  → tiles
```

---

## 4.2 Обеспечение отказоустойчивости

| Уровень             | Механизм                                        |
| ------------------- | ----------------------------------------------- |
| **L4**              | Active/Standby, автоматическое переключение VIP |
| **L7**              | Схема N + 1                                     |
| **NGINX → backend** | health checks и исключение недоступных узлов    |
| **Backend**         | Репликация сервисов                             |

При отказе:

* одного L7 → его нагрузка перераспределяется
* одного backend → запросы уходят на другие инстансы
* одного L4 → активируется резервный VIP

---

## 4.3 Расчёт количества балансировщиков

* **Пиковый трафик:** 102.6 Гбит/с
* **Пиковая нагрузка:** 13 086 RPS

---

### 1. Расчёт L4

L4 работает на уровне TCP и не выполняет сложной логики, поэтому его ограничение — сеть.

При использовании 100GbE:

102.6 Гбит/с ÷ 100 Гбит/с ≈ 1.03 → 2 сервера

С учётом резервирования (Active/Standby):

**Итого: 2 сервера L4**

---

### 2. Расчёт L7

Ограничение — пропускная способность сети.

Примем:

**25 Гбит/с на сервер**

Расчёт:

102.6 ÷ 25 ≈ 4.1 → 5 серверов

С учётом N + 1:

5 + 1 = **6 серверов**

---

## 4.4 Распределение запросов

### Как система выбирает сервер

| Этап                        | Описание                                                     |
| --------------------------- | ------------------------------------------------------------ |
| **1. Вход**                 | Пользователь обращается к сервису по единому IP (VIP)        |
| **2. L4**                   | Балансировщик распределяет TCP-соединение на один из 6 NGINX |
| **3. L7**                   | Выбранный NGINX принимает HTTPS и анализирует запрос         |
| **4. Маршрутизация**        | По URL определяется нужный сервис                            |
| **5. Балансировка backend** | Запрос отправляется в соответствующий кластер                |
---

### Как маршрутизируются API

| Запрос| Сервис| Балансировка|
| --- | --- | --- |
| `/api`    | `api`    | round robin между backend |
| `/search` | `search` | round robin|
| `/route`  | `route`  | round robin|
| `/tiles`  | `tiles`  | round robin + кэширование |
---

## 4.5 Распределение ролей между серверами

Все L7-балансировщики являются универсальными узлами и обрабатывают все типы запросов.

Сервера **L7-1, L7-2,...,L7-5** - активны, они обрабатывают весь тип трафика (`api`, `search`, `route`, `tiles`)
**L7-6** - резервный подключается при отказе одного из узлов

## 4.6 Архитектурное обоснование

| Вопрос| Обоснование|
| --------------------------------------- | -------------------------------------------------------------------------- |
| **Почему используется L4 + L7**         | L4 распределяет соединения между NGINX, L7 выполняет всю прикладную логику |
| **Почему не только L7**| Требуется единая точка входа (VIP) и балансировка между фронтовыми узлами  |
| **Почему не только L4**| L4 не умеет SSL termination и маршрутизацию по URL|
| **Почему все API за одним NGINX**       | Упрощение архитектуры и повышение отказоустойчивости|
| **Почему L7 — основной уровень логики** | Вся бизнес-логика маршрутизации находится на HTTP-уровне|
